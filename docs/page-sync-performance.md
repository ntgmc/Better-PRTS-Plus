# 页面同步测量（问题 09，方案未采纳）

试验方案减少了工具栏重复 DOM 更新和局部结构同步耗时，但整页脚本时间中位数上升，长任务也未改善。按用户决定不采纳该方案，产品代码、对应回归测试及构建文件已恢复到测量前状态；本报告和录制仅保留试验记录。

## 测量方法

- 页面：`https://prts.plus/`，Chromium `153.0.8010.12`，视口 `1280 × 900`。
- 使用基线和试验方案的实际构建脚本，临时注入函数计数、DOM 创建 API 计数、事件注册计数和计时；产品代码不包含这些计数。
- `GM_*` 使用独立内存存储；预置 `resourceVersion: 1` 的当前资源缓存和 432 名干员，启用完美阵容筛选，其余设置使用默认值。
- 基线和试验各三轮。每轮重新打开页面，从 10 张卡片开始，注入脚本后预热 2 秒，再依次执行下列场景。
- 空闲：等待 9.5 秒。搜索：依次输入 `1-7`、`12-17`、空字符串并按 Enter，每次等待 1.8 秒。翻页：点击原站 `Load More`，等待卡片从 10 张增至 20 张，再等待 1.2 秒。
- 使用 CDP `Profiler` 保存每个场景的 CPU 录制，用 `Performance.getMetrics` 的差值记录全页 `ScriptDuration`；通过 `PerformanceObserver` 收集超过 50 毫秒的长任务。
- 工具栏 DOM 变更以目标属于 `#prts-filter-bar` 的 `MutationRecord` 计数，覆盖属性、子节点和文本变更；它不是页面全部 DOM 写入量。

所有样本启用相同的计数和采样，绝对耗时包含测量开销。先完成三轮基线录制，再运行快速返回的试验方案并完成三轮复测；没有剔除异常轮次。原始 JSON、18 份 `.cpuprofile`、试验快照和复测工具收录在交付附件 `better-prts-page-sync-09-recording.zip` 中，归档中的 `optimized` 文件仅对应未采纳的试验方案。

## 调用与工具栏 DOM 工作

下表均为“基线 → 试验方案”。调用和变更次数列出各轮一致的值，存在波动时列范围。

| 场景 | 结构同步调用 | 按钮构建调用 | 工具栏 DOM 变更 | 事件新增 / 移除 |
| --- | --- | --- | --- | --- |
| 空闲 9.5 秒 | 3 → 3 | 21 → 0 | 144 → 0 | 21 / 21 → 0 / 0 |
| 搜索三次 | 11 → 11–12 | 77 → 0 | 528 → 0 | 77 / 77 → 0 / 0 |
| 加载更多 | 6 → 5–6 | 42 → 0 | 288 → 0 | 42 / 42 → 0 / 0 |

基线每次同步都会更新 7 个按钮的图标、标签和事件。空闲三轮均调用 HTML 创建 API 39 次、SVG 创建 API 36 次，试验方案中均为 0。该计数不包含 `DOMParser`、`importNode` 等内部创建的节点，也不代表完整堆分配量或 GC 成本。

## 耗时与长任务

耗时单位为毫秒，数值为三轮累计耗时的中位数；函数耗时包含其内部调用，不应相互相加。

| 场景 | `syncPageScaffold` | `injectFilterControls` | 全页 `ScriptDuration` |
| --- | --- | --- | --- |
| 空闲 9.5 秒 | 4.0 → 1.7 | 3.2 → 0.3 | 27.702 → 31.961 |
| 搜索三次 | 14.2 → 4.2 | 11.1 → 0.4 | 212.270 → 337.243 |
| 加载更多 | 9.0 → 3.1 | 7.0 → 0.1 | 90.709 → 103.705 |

| 场景 | 三轮长任务数量：基线 | 三轮长任务数量：试验 | 最长任务：基线 → 试验 |
| --- | --- | --- | --- |
| 空闲 9.5 秒 | 0、0、0 | 0、0、0 | 无 → 无 |
| 搜索三次 | 2、0、0 | 0、7、1 | 170 → 335 |
| 加载更多 | 1、1、1 | 0、4、1 | 60 → 428 |

复测第二轮的整页耗时明显上升：搜索 `ScriptDuration` 为 1411.699 毫秒，加载更多为 571.334 毫秒；该轮工具栏仍为零按钮重建、零 DOM 变更。CPU 录制中原站布局读取、卡片处理和垃圾回收的采样时间也增加了，现有数据不足以确定整页波动的原因。

试验确认了局部重复工作的减少，但整页脚本时间中位数和长任务没有下降，未能证明整页 CPU、GC 或流畅度收益。空闲时基线结构同步的绝对成本也较小，约为每 9.5 秒 4 毫秒，因此按用户决定撤回优化，继续使用基线实现。

## 试验实现与恢复验证（未采纳）

试验方案曾在工具栏上保存已渲染的账号、名称、干员数量、森空岛同步摘要及显示/筛选/练度状态，同时保存节点的父子关系。再次同步时先寻找当前搜索栏；状态、位置和结构都匹配才直接返回。状态变化或结构丢失时继续走原有构建流程。

试验沿用了原有 DOM 观察、3 秒定时同步和筛选协调器。试验回归覆盖了账号切换、重命名、数量变化、同步摘要增删、模式变化、搜索栏移动、按钮/行/图标/标签/整栏丢失，以及禁用页面和恢复。

真实浏览器验证了试验方案的节点恢复、工具栏归位、单次点击只切换一次筛选、定时恢复整栏后重新应用当前筛选，以及同页路由变为 `/create` 后移除工具栏、返回列表后恢复。试验回归先在基线上因重复构建 7 个按钮失败，再在试验方案上通过；这些记录保留在归档中，对应的产品代码和回归测试已撤回。
